# pj_custom_widgets

## Purpose

The "Custom Widget" panel: a dock whose content is a Qt widget created by a Widget plugin (the SDK family `Widget`, ABI in `pj_plugins/widget_protocol`). The module owns what the host does for such a panel: wiring series to the widget's named inputs, resolving the value at the tracker time, pushing it to the plugin, persisting the panel in the layout, and destroying the plugin's objects in a safe order. The plugin never sees topics, datasets or the data store.

Intent and requirements: [docs/REQUIREMENTS.md](./docs/REQUIREMENTS.md).

## Layout

- `core/` (`pj_custom_widgets_core`): no widget class.
  - `WireSample.{h,cpp}`: the latest sample of one wire at an instant (scalar, text or object), its identity hash for change detection, and its conversion to `PJ_widget_value_t`.
  - `SettingsSchema.{h,cpp}`: `parseSettingsSchema`, the widget type's `settings` declaration parsed into `SettingDecl`s, read by the dock (manifest defaults) and the shell's config panel (the form).
  - `WidgetBindings.{h,cpp}`: the wires of one panel (series wired to an input slot), reconciliation by input name, resolution against the catalog from the persisted identity, and the `<input>` XML.
- `widget/` (`pj_custom_widgets`): `CustomWidgetDockWidget` (`QWidget` + `IDataWidget`) and `MissingWidgetPlaceholder`.
- `tests/`: `pj_custom_widgets_tests` (unit and dock tests against an in-process plugin, `in_process_widget_plugin.h`, whose `faulty_widgets` vtable and `g.*` switches drive the error paths), `test_widget_plugin.cpp` (a real Qt plugin library for the end-to-end runs), `E2E.cmake` + `run_custom_widget_e2e.cmake` (registered from `pj_app/CMakeLists.txt`, where the `pj_app` target exists). Every end-to-end variant is Linux only: the runs redirect the user profile (settings, extension store, the active-widgets record) through `XDG_CONFIG_HOME` / `XDG_DATA_HOME` / `HOME`, which only Linux honours, and the app has no profile-directory override yet. The `after_kill` variant hard-kills a run with the widget live, checks the record it left (`active_widgets.<pid>.json`), plants a record under the pid of the live cmake process, then checks that the next run reports the dead run's record and not the live one, consumes only the dead one, still restores the widget and exits leaving no record of its own.

## Rules that hold the design together

- **Every plugin call is on the GUI thread.** `inputs_changed` arriving from inside one of the plugin's own calls is deferred with `QTimer::singleShot(0)`; the input list never changes under a running `on_update`.
- **Inputs are matched by name, never by position.** `WidgetBindings::setInputs` is the only reconciliation point. A failed `inputs()` (the plugin reported an error, or returned a list `WidgetHandle::inputs` refuses: a null array with a count, an empty or duplicate name, an unknown kind, an impossible string) is never reconciled against, since an empty list would drop every wire: `readInputs()` disables the panel through `disablePlugin`, whose preserved element keeps the wires as they were.
- **`on_update` runs only when a wired sample changed.** The dock hashes the identity of every wire (stamp and number, the stamp alone for text, entry uid for objects, display offset) and skips the call when the hash is unchanged. Object payloads are fetched only after the hash changed, and only for an entry the wire does not already hold; a text string is read only when its row stamp moved (the dock keeps each wire's previous sample until the wiring changes). The per-tick path (`pushValues`) reuses member scratch vectors and copies no string.
- **Placeholders and errors.** A widget that cannot be created (missing library or type, Qt build mismatch, a failed creation) or that is disabled after an error shows `MissingWidgetPlaceholder` with the reason, and `isMissing()` is true. A crash inside the plugin (SIGSEGV) is not catchable in the dock: the active-widgets record covers it at the next start.
- **Synchronous destruction.** `releasePlugin()` detaches the plugin's widget (`setParent(nullptr)`) and then destroys the handle, in `aboutToBeDiscarded()` and in the destructor. Both are needed: a panel closed during the session is scheduled for deferred deletion, so only `aboutToBeDiscarded()` ends its plugin before the session or the event loop can reach it; the destructor covers window teardown, where `~MainWindow` deletes the docks (`delete ui_->tabbedPlotWidget`) before the session unloads anything. Never `deleteLater` on anything the plugin created. `pj_plotting`'s `DockWidget::clearCurrentContent` calls `IDataWidget::aboutToBeDiscarded()` right before it schedules the dock's content for deferred deletion, so the plugin's widget dies before the session or the event loop can reach it; `releaseObjectWidget` (the content moves to another dock) does not call it, and the dock must tolerate its own later deletion. The library is never unloaded (the SDK loader keeps it mapped for the life of the process), so the plugin's code is mapped for as long as its widget can be called.
- **A widget that cannot be created keeps its layout element.** Missing (or disabled) library, missing type, Qt build mismatch (`qt_compatible == false`, never call `create_qwidget`), a creation failure or an error during creation all give the placeholder and an `xmlSaveState` that returns the loaded element verbatim.
- **The host stores the whole settings JSON** and sends it whole through `load_config` on every change and on restore, with the manifest `default` filled in for every declared key the stored JSON lacks (`withDefaults`, from the declarations parsed once per bind): a brand-new panel's first `load_config` is the full defaults object, never `{}` (a type that declares no defaults and has no stored settings gets no `load_config` at creation). `settingsJson()` is defaults, then the stored values, then the plugin's own `save_config` keys laid over them (a colliding state key wins); that is what the layout persists, so the saved `<config>` carries every key. A declared key with no `default` appears only once the user set it.
- **Every plugin call goes through `callPlugin`** (or `callOrDisable`, which disables on an exception): a call-depth rollback plus a catch, no allocation on the success path. An exception it returns makes the dock `disablePlugin(reason)`: `releasePlugin()`, the element kept in `preserved_` (built from the dock's own state, never by asking the plugin), wires and inputs cleared, the placeholder with "This widget was disabled after an error", a `kError` to the sink, `inputsChanged` + `bindingsChanged`. From a const path (`settingsJson` during a layout save) the disable is deferred to the event loop and skipped if the dock was rebound in between (`bind_generation_`). Slots are `PJ_NOEXCEPT`, so what this realistically catches is the host's own conversion of what the plugin returned (a string length no `std::string` can hold, an allocation failure); a plugin built on `WidgetPluginBase` contains its own exceptions in the SDK trampolines (an exception in `onUpdate` is swallowed there and the panel stays live). `destroy` and `~WidgetHandle` are noexcept, so `releasePlugin` has no catch.
- **The active-widgets record** (`setActiveWidgetsMarker`, this process's record, shared from `pj_app`'s `CustomWidgetController`): the dock adds `plugin_id/type` right before `createHandle` (the first plugin call) and removes it in `releasePlugin` after the handle died, so the file names exactly the panels whose plugin code was live. Null marker = nothing recorded (the module's own tests, the browser).

## Persistence

One fixed tag, `CustomWidget`, with `plugin`, `type`, `plugin_version`; one `<input name slot kind dataset_id dataset_source dataset_path topic field/>` per wire; `<config><![CDATA[json]]></config>`. On restore the wires load before `create_qwidget`, so a widget can query their history while building its view. A wire's identity is a `SavedSeriesPath`, the type the layout uses for curves. The panel writes the full `dataset_path` itself, and every `<CustomWidget><input>` then goes through `LayoutXml`'s three passes like a transform input (`forEachCustomWidgetInput`): a file save makes the path layout-relative and strips an id it cannot validate, and a generic layout drops all three qualifiers. The panel re-resolves through `CatalogModel::resolveCurveKey` (scalars) or `SessionManager::resolveObjectDatasetIdentity` (objects). Wires that do not resolve stay pending, are written back verbatim and are retried when the catalog adds or changes items. A pending wire still needs its topic subscribed on a demand-driven stream, so `pendingDemands()` lists one `PendingWireDemand` (topic, plus the dataset its saved identity names when that one is loaded) per distinct pending topic, and the shell's `PendingDisplayBinder` holds a demand reference for each (`addPendingCustomWidgetWire`, from `MainWindow::collectPendingDisplayBindings` next to the scene loop). The dock keeps its own retry; the binder only holds the reference and drops it once no pending wire of the dock names the topic (checked on `bindingsChanged`), when the dock is destroyed, or on `clear()`.

## Public surface for the shell

`CustomWidgetDockWidget`: `setActiveWidgetsMarker(marker)`, `bindToWidget(plugin_id, type)`, `inputs()`, `bindings()`, `setBinding(input, slot, key)` (`WidgetBindings::kNewSlot` appends), `canBind(input, key)` (what the side panel's series chooser offers), `removeBinding`, `settingsSchemaJson()`, `settingsDeclarations()`, `settingsJson()`, `applySettings(json)`, `isMissing()` / `missingReason()`, `displayedTopics()`, `pendingDemands()`; signals `bindingsChanged`, `inputsChanged`, `workspaceChanged`. Demand is registered with `TopicDemandController::registerCustomWidgetDock`; construction and wiring live in `MainWindow::makeSceneDock` (kind `"CustomWidget"`) and `MainWindow::createCustomWidgetDock`; the side-panel pages and the record in `CustomWidgetController`.
